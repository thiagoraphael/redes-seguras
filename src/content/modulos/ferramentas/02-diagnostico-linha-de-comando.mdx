## Antes de proteger, enxergar

Não dá para defender uma rede que você não conhece. Antes de configurar firewall, trocar senha ou instalar antivírus, o técnico precisa responder perguntas básicas: qual é o IP desta máquina? Por onde ela sai para outras redes? Quais portas ela deixa abertas? Aquele servidor está fora do ar ou é a rede que caiu?

Seis comandos respondem quase tudo isso. Todos vêm no Linux, todos rodam no terminal, e você vai usar todos no lab desta aula.

| Pergunta | Comando |
| --- | --- |
| Qual é o meu IP? | `ip a` |
| Por onde eu saio para outras redes? | `ip r` |
| Que portas estão abertas aqui? | `ss -tulpn` |
| Aquela máquina responde? | `ping` |
| Por onde o pacote passa até lá? | `traceroute` |
| Esse nome aponta para qual IP? | `dig` |
| O que está passando no cabo agora? | `tcpdump` |

Os exemplos abaixo são do mesmo servidor que você vai usar no lab, o **srv-lab**. A rede é fictícia: só endereços privados (192.168.56.0/24 e 10.0.0.0/24), que não existem na internet.

## ip: quem é esta máquina na rede

**O que faz:** mostra e configura interfaces de rede, endereços e rotas. Faz parte do pacote iproute2 e substitui os antigos `ifconfig` e `route`, que muitas distribuições nem instalam mais.

Você vai usar dois "objetos" do `ip` o tempo todo: `address` (abreviado `a`) e `route` (abreviado `r`).

**Quando usar:** sempre que a máquina "não tem rede". Sem `inet`, o problema é endereçamento (DHCP, cabo, placa). Sem linha `default`, a máquina fala com a rede local mas não sai dela. Quer saber por qual rota um destino específico vai? `ip route get 10.0.0.15` responde.

## ss: o que está escutando nesta máquina

**O que faz:** lista os sockets, ou seja, as conexões abertas e as portas em escuta. É o substituto moderno do `netstat`.

Cada porta escutando é uma porta de entrada. Para segurança, este é um dos comandos mais importantes da aula: serviço que você não sabia que estava rodando é serviço que você não está protegendo.

As opções mais usadas, juntas, formam o famoso `ss -tulpn`: **t**cp, **u**dp, **l**istening (só os que escutam), **p**rocessos e **n**umérico (mostra 22 em vez de "ssh").

**Por que o sudo?** Sem ele, o `ss` mostra as portas, mas a coluna Process fica vazia para programas de outros usuários (o nginx roda como root). Com `sudo`, você vê tudo.

**Quando usar:** para conferir se um serviço subiu ("o site não abre, o nginx está mesmo escutando?") e para auditar a máquina ("tem alguma porta aberta que não deveria?"). Para ver conexões já estabelecidas em vez de portas em escuta, tire o `-l`: `ss -tn`.

## ping: alguém aí?

**O que faz:** manda pacotes ICMP do tipo *echo request* e espera *echo reply*. É o "alô, tá me ouvindo?" das redes.

No Linux o ping **não para sozinho**: ele fica mandando até você apertar <kbd>Ctrl</kbd>+<kbd>C</kbd>. Por isso use sempre `-c` com a quantidade de pacotes.

**Cuidado com a conclusão.** Ping sem resposta não prova que a máquina está desligada. Muitos firewalls bloqueiam ICMP de propósito. O contrário também vale: responder ping não quer dizer que o site ou o serviço está funcionando. Ping testa a rede, não a aplicação.

Duas mensagens que você vai encontrar: `Destination Host Unreachable` (ninguém na rede local respondeu por aquele IP) e `Temporary failure in name resolution` (o problema nem chegou no ping, foi o DNS que falhou).

## traceroute: o caminho até lá

**O que faz:** mostra cada roteador (salto) no caminho até o destino. Ele manda pacotes com TTL 1, depois 2, depois 3... Cada roteador que zera o TTL descarta o pacote e devolve um ICMP *time exceeded*, se identificando. No Linux, por padrão, são 3 sondas por salto e no máximo 30 saltos.

<SaidaComentada
  comando="traceroute -n 10.0.0.15"
  notas={[
    { linha: 2, texto: 'Salto 1: o gateway da nossa rede. Os três tempos são as três sondas.' },
    { linha: 3, texto: 'Salto 2: o roteador da outra rede (10.0.0.0/24) respondeu.' },
    { linha: 4, texto: '<code>* * *</code>: nenhuma das três sondas teve resposta a tempo. O problema está daqui para frente.' },
  ]}
>
```
traceroute to 10.0.0.15 (10.0.0.15), 30 hops max, 60 byte packets
 1  192.168.56.1  0.548 ms  0.480 ms  0.545 ms
 2  10.0.0.1  1.21 ms  1.22 ms  1.66 ms
 3  * * *
 4  * * *
```
</SaidaComentada>

**Quando usar:** quando o ping falha e você quer saber **onde** o caminho quebra. Se o primeiro salto já não responde, o problema está perto (cabo, gateway). Se para lá na frente, o seu lado está ok. O `-n` evita que ele tente traduzir cada IP em nome, o que deixa tudo mais rápido.

Asteriscos isolados no meio do caminho nem sempre são problema: alguns roteadores simplesmente não respondem a esse tipo de sonda e repassam o tráfego normalmente.

## dig: perguntando ao DNS

**O que faz:** consulta servidores DNS e mostra a resposta completa. É a ferramenta para responder "esse nome aponta para onde?" e "quem respondeu isso?".

Atalhos úteis: `dig +short NOME` mostra só a resposta; `dig -x IP` faz a consulta reversa (de IP para nome); `dig @SERVIDOR NOME` pergunta para um servidor específico.

**Quando usar:** quando "o site não abre mas o ping no IP funciona". Nesse caso o problema costuma ser DNS. Para segurança, o dig também ajuda a perceber quando um nome está apontando para um IP estranho, que é exatamente o que acontece quando alguém altera o DNS de um roteador (você vai ver um exemplo disso na disciplina de Defensiva).

## tcpdump: vendo os pacotes passarem

**O que faz:** captura os pacotes que passam por uma interface e mostra um resumo de cada um. É o "raio X" da rede.

Capturar tráfego exige privilégio de administrador, por isso ele roda com `sudo`. Opções que você vai usar sempre: `-i` escolhe a interface, `-n` não converte IPs e portas em nomes, `-c N` para depois de N pacotes. Depois das opções vem o **filtro**: `port 53`, `host 192.168.56.30`, `icmp`, `tcp and port 8080`...

É também a ferramenta que mostra por que protocolos sem criptografia (HTTP, Telnet, FTP) são perigosos: o conteúdo aparece inteiro. No próximo encontro você vai ver isso com uma senha.

## Um roteiro de diagnóstico

Quando algo "não funciona", vá de baixo para cima. Cada passo elimina uma camada de suspeitos:

1. `ip a`: a interface está UP e tem IP?
2. `ip r`: existe rota default?
3. `ping` no gateway: a rede local funciona?
4. `dig` no nome: o DNS resolve?
5. `ping` ou `traceroute` no destino: o caminho existe? Onde quebra?
6. `ss` no servidor: o serviço está mesmo escutando na porta certa?
7. `tcpdump`: o pacote chega? A resposta sai?

Agora vá para o lab e use esse roteiro nas missões.
